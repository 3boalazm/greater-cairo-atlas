# Mobile performance — November 2026

The supplied 16 November production PageSpeed mobile baseline was 37, with FCP 3.6 s, LCP 5.6 s, TBT 4,300 ms and CLS 0.001. No post-change PageSpeed/Lighthouse score is claimed here: the production site has not been deployed from this branch, and the sandbox has no working browser or production database.

## Changes

- The two unchanged OSM context road sources start empty. After the map's first `idle`, the enabled base network is assigned by URL; detail is assigned only at zoom **11**, its existing layer's minzoom. A disabled network is not downloaded until enabled. MapLibre loads and processes these URLs in its worker. The URLs now have a one-day browser cache and a seven-day shared cache. Local Next responses negotiate gzip; production CDN compression still needs deployment verification. No coordinates were rounded: this batch does not modify source data or geometry precision.
- The home page formerly embedded the full feature collection in the RSC/HTML payload, alongside the entity search index and dated timeline facts. It now embeds the search, timeline, stats and small precomputed conflict metadata, and fetches zoom-appropriate feature data from the existing API. If that API fails, the same checked-in snapshot previously embedded in HTML is available as a filtered fallback endpoint. Deep links still select immediately and the camera waits for geometry. The 31 Batch 20 features are included in the fallback.
- MapLibre/MapView was already loaded by `next/dynamic` with `ssr: false`, behind the header/search shell; the entity panel is now separately lazy-loaded. The large home chunk in the comparable local baseline included the Arabic fact-label dictionaries, Zod schema validation, and panel/UI code. Fact-label dictionaries now load with the panel, and timeline status values no longer import the Zod schema into the initial client graph. This is based on local build contents; the exact deployed PageSpeed chunk hash can differ between builds.
- Next already emits and minifies the main stylesheet and loads MapLibre's CSS in a separate dynamic stylesheet, rather than including the MapLibre stylesheet in the first document's stylesheet links. The main stylesheet remains render-blocking; no unverified critical-CSS rewrite was attempted.

## Comparable local production builds

Both builds were run with `npm run build` and `next start` locally, no `DATABASE_URL`, `Accept-Encoding: gzip`. Raw sizes are bytes; gzip JS sizes use Node gzip level 9. HTML is an actual gzip HTTP response. These are **not** PageSpeed mobile timings, browser network traces, or measurements of Vercel's compression.

The <100 KiB HTML goal is met for the measured **gzip transfer**, not the uncompressed document. The local gzip road responses are 585,372 B (base) and 875,839 B (detail); both are unchanged data, and their timing is deferred rather than their payload eliminated.

## Remaining verification and limitations

- Run PageSpeed and a real mobile browser against the preview/deployment to measure FCP, LCP, TBT, CLS, total requests, cache/compression, and interactions at zoom 11 and higher. Verify Arabic/English, RTL, search, feature clicks, panel, filters, timeline, deep links, and first-visit guide. No real-browser interaction check was possible in this sandbox.
- The database features API still returns JSON to the main thread for filtering and selection; only the large road-network parsing is handed directly to MapLibre's worker. When the database API is unavailable, the snapshot fallback is intentionally complete and can itself be large (local gzip response about 573 KB). Moving all feature filtering/parsing to workers or vector tiles remains future work.
- The normal `/api/atlas/features` database path could not be exercised locally without `DATABASE_URL`; the full suite exercises its PostGIS query with PGlite. Verify the deployed database has imported Batch 20 before interpreting production results.

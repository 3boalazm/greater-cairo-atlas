# Homepage performance — November 2026

## Measurement and limitations

Production payload and mobile Lighthouse were **not measured**: this sandbox permits outbound connections only to the configured GitHub, npm and PyPI hosts, and no Chrome/Chromium or Lighthouse executable is installed. Do not treat the local figures below as production network or Lighthouse results. Repeat from an unrestricted mobile Lighthouse environment against the live deployment before drawing conclusions about field performance.

As a reproducible proxy, the Batch 18 branch was built using `npm run build` and served locally with `next start`; `curl` requested `/en` with `Accept-Encoding: identity`. On the local production-mode server:

| Response | Uncompressed response body bytes | Method |
|---|---:|---|
| Homepage HTML | 3,282,610 | `curl -H 'Accept-Encoding: identity' http://127.0.0.1:3000/en` |
| RSC response | 3,039,290 | Same request with `RSC: 1`, following Next.js redirect to `?_rsc` |

The HTML embeds the initial RSC payload; these are alternative responses, **not additive**. Server compression, CDN caching, mobile device speed and live deployment behaviour were not measured.

## Likely main contributors (code inspection, not Lighthouse attribution)

1. The homepage serializes all 2,983 feature geometries into `initialFeatures` for the client map; source `data/features/features.geojson` is 8,181,320 bytes on disk.
2. The same initial payload also includes the entity catalogue, aliases, feature provenance and status-timeline facts, increasing serialization and hydration work.
3. Large separate road context GeoJSON resources may cost additional network and map parsing when loaded: `public/road-network.geojson` is 5,646,696 bytes and its detail counterpart is 6,444,755 bytes on disk. These file sizes are not measured homepage transfer sizes.

## Follow-up proposal

Profile with Lighthouse mobile and browser network/CPU traces on the actual production URL. Consider lazy loading/viewport filtering for initial geometry and avoiding repeated per-feature metadata, while preserving the current map and attribution. PMTiles/vector tiles could eventually deliver only needed zoom/viewport data; this is a proposal, not implemented in Batch 18. Evaluate licensing, source attribution and offline/export fidelity before any format migration.
